# UIデザイン(claude design)

[Purpose: 画面変更を伴う作業で、見た目・情報設計を実装や設計書より先に確定させる]

kiroの公式フェーズには含まれないが、本プロジェクトでは必須ゲートとして扱う。エージェントは画面変更を検知したら、本ドキュメントに従い進行を止めるか、ユーザーにclaude designへの着手を促す。

## 原則

- 利用者に見える画面の構成・見た目・操作感を変える場合は、必ずclaude designでモックを作成し、採用案を確定してから設計・実装に進む
- Google Stitchは使わない。画面デザインの対話的確定手段はclaude designのみとする
- 既存のカンバン・案件管理などで確立した視覚言語(配色・`primary`・Modal・フォーム・一覧のchrome)を踏襲し、画面ごとに別の見た目を作らない
- 確定内容は推測で埋めない。モックとユーザー合意が設計の入力になる

## 適用条件(必須)

次のいずれかに該当する場合、本ゲートを適用する。

- 新規画面・新規主要コンポーネントの追加
- 既存画面のレイアウト・情報設計・主要操作フローの変更
- 画面分離・統合、ナビ項目の追加/移動に伴う画面責務の再編
- 見た目の刷新(配色・余白・一覧/フォーム/モーダル構成の揃え直しを含む)

次は適用外とする(見た目の再設計を伴わないもの)。

- 文言・ラベルの修正のみ
- バグ修正で既存レイアウトを維持したまま挙動だけ直す場合
- 画面を持たないバックエンド・スキーマ・steering/spec文書のみの変更

判断に迷う場合は適用する側に倒す。

## ワークフロー上の位置

```
requirements → [validate-gap] → claude design(本ゲート) → design → [validate-design] → tasks → impl
```

- 推奨タイミングは、要件が固まった後〜`/kiro-spec-design` の直前
- `/kiro-spec-design`・`/kiro-spec-tasks`・`/kiro-impl` に進む前に、適用対象なら確定済みであることを確認する
- デザイン未確定のまま画面UXの詳細をdesign.mdやtasks.mdに書き下ろさない
- 実装後にデザインを回すことは禁止する。`task-case-calendar`では実装後確定となり、requirements/design/tasksの事後改訂が発生した

## 実施と記録

1. claude designで対象画面のモックを作成し、案の比較があれば採用/不採用を決める
2. 確定内容を当該スペックの`research.md`に「ビジュアルデザイン確定(claude design連携)」として追記する
   - 採用したレイアウト・主要コントロール・不採用案
   - モック名やプロジェクト名など、後から辿れる識別情報
3. `/kiro-spec-design`では、その確定内容をComponents / File Structure / Flowsに反映する
4. 実装タスクは確定モックを参照する形で分解する

## 強制(エージェント向け)

画面変更がスコープに含まれるスペックまたは作業について:

- claude design未実施、または`research.md`にビジュアルデザイン確定の記録がない場合
  - `/kiro-spec-design`へ進まない
  - 画面UXの詳細設計・タスク分解・実装を開始しない
  - ユーザーに「先にclaude designで画面を確定する」旨を伝え、待機する
- 要件に「claude designで確定する」と書いてあっても、実モックとresearch記録がなければ未充足とみなす
- ユーザーが明示的に本ゲートのスキップを指示した場合のみ例外とする。その場合は理由を`research.md`に残す

## 本スペック以降の期待

`recurrence-holidays-ux`のように画面分離やUX刷新を含むスペックは、ギャップ分析の次に本ゲートを挟む。API削除やスキーマ整理など非UI部分の設計議論は並行してよいが、画面構成・操作感に依存する設計判断はデザイン確定後に行う。
