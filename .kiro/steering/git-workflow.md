# Gitワークフロー

[Purpose: ブランチ・コミット・push・PRに関する運用ルールをまとめる]

## ブランチ

- 基本的に `.kiro/specs/` のスペック1つに対して1ブランチを作成する
- ホットフィックスなど、スペックに紐づかない単発の作業はこの限りではない
- 新しい指示が、既にpush済みだが未マージのブランチ/PRと同じ話題・同じファイルを対象にしている場合は、新規ブランチを切らずそのブランチに追記コミットする。新規ブランチを切ると重複するだけになるため、作業前にmainだけでなく関連する未マージブランチの有無も確認する

## コミット

- `/kiro-impl` の実装単位(タスクごと)にコミットを行う。まとめて1コミットにしない
- コミット前にコミットメッセージのルール([[commit-message]])を満たしているか確認する。違反している場合は `.githooks/commit-msg` フックがコミット自体を拒否する([[commit-message]]の「強制」節を参照)

## 履歴の整理

- 対象スペックの `tasks.md` が全タスク完了になり、かつユーザーから指示があったときに限り、それまでのブランチのコミットを整理する
- 未push・ローカルのみの範囲で行う(reflogで復元可能な操作に留める)

### squashしてよいもの・残すべきもの

判断基準は「そのブランチの中で紆余曲折があっただけか」「別の仕様・不具合として意味のある履歴か」で分ける。

- **squash対象**: 同一ブランチ内で「機能を実装する→コミット」「レビューでその機能自体の不具合が見つかる→修正してコミット」のように、最初のコミット単体では未完成・役に立たない状態になっている場合。この手の紆余曲折を逐一残してもコミットが汚れるだけなので、最終的に意味のある単位(「機能構築」「不具合修正」「ドキュメント整合」など)にまとめる
- **残すべき履歴**: 別のスペック・別の時期に実装した機能の不具合を、今回のブランチで修正した場合。これは「その仕様のまま一定期間動いていた」という事実そのものが記録として重要なので、squashでまとめて消してしまわない(別コミットのまま、あるいは別ブランチ/PRとして残す)

## ローカル検証のスキップ

- 差分が `.kiro/`、`.githooks/`、`*.md` などドキュメント・steering・spec関連のパスのみで、アプリのソースコード(`backend/`、`frontend/`のコード本体、`docker-compose.yml`等)を一切含まない場合、push前のローカルテスト/ビルド検証(`docker compose run ... npm run test` 等)は意味がないためスキップしてよい
- GitHub Actions側のCI(`.github/workflows/ci.yml`)にはパスフィルタがなく、ドキュメントのみの変更でも全ジョブが実行される。これはローカル検証のスキップとは別物で、CI側の実行有無はこのルールでは変えない

## push / PR

- pushはユーザーからの明示的な指示があるまで行わない
- push後、PR作成用のGitHub URL(`.../pull/new/<branch>`)を提示する
- PRの実際の作成(`Create pull request`のクリック)はユーザーが行う。Claude側では代行しない
