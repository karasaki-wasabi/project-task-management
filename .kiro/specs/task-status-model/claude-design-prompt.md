```text
プロジェクト名の提案: task-status-model（タスク管理 — 開発段階の種別とステータスの再定義）

目的
社内向けタスク/案件管理アプリ「Task Delivery Management」で、「タスクが終わったこと」の判定方法を変更する。これに伴い既存4画面の情報設計が変わるため、その差分を確定したい。新規画面は作らない。既存のデザインシステムを厳密に踏襲し、専用の別ブランドにしない。Google Stitch は使わない。モックは実装前の確定用。

添付したスクリーンショットの扱い（最優先）

- 今回、開発段階に「種別」を導入する。種別は 通常 / 完了 / 中止 の3つ
  - 完了種別の段階と中止種別の段階は、システム上つねに1つずつ存在する。削除できない。新規作成した段階は必ず通常種別になる。種別を後から変更する手段もない
  - タスクが完了種別の段階に入った時刻をもって「完了」とする。中止種別に入ったタスクは「終わったが消化していない」扱いになる
- 「ステータス」は開発段階とは別物で、いま置かれている段階の中での作業状態を表す。値は 未着手 / 作業中 / 引継待ち / 保留 の4つ

- 完了・中止の段階（以下「終端段階」）にあるタスクには、段階内の作業が存在しない。したがってステータスという概念が適用されず、画面に出さない
- この変更の眼目は「完了」という語が2箇所で違う意味を持っている状態の解消にある。モック上でも「完了」がタスク全体の完了だけを指すようにすること

- ログイン済み。sticky ヘッダーの左にアプリ名「Task Delivery Management」、その右にナビリンク、右端に現在ワークスペースの切替と表示名／ログアウト

参照する既存の視覚言語（厳守）

作ってほしい画面・要素（デスクトップ幅を主、モバイルも破綻しないこと）
すべて既存画面の差分。現状を壊さないこと。

1) 開発段階マスタ画面（/kanban/stages）★情報要素が増えるので最重要
現状:
- h1「開発段階マスタ」
- 白カードの登録フォーム: 段階名の入力（placeholder「段階名(例: 仕様未確定)」）＋ 青の「登録」ボタン

  段階名(flex-1) / 「↑」/「↓」/「名称変更」/「削除」。ボタンはすべて Secondary の text-xs

変更してほしい点:
- 各行に種別（通常 / 完了 / 中止）が分かる表示を足す
- 完了・中止の行では「削除」を提示しない。または無効化して理由が分かるようにする（どちらが良いか案を出して推奨を示す）
- 「名称変更」「↑」「↓」は完了・中止の行でも使える（改名と並び替えは許可されている）
- 通常段階と終端段階が一覧の中で見分けられること。ただし行の背景色を塗り分けるような重い区別は避けたい
検討してほしい案:
- 種別をバッジで示す / アイコンで示す / 通常段階には何も出さず終端段階にだけ印を付ける、の比較

2) カンバンボード（/kanban）
現状:
- 横スクロールする列。各列は w-72 の rounded-lg border-slate-200 bg-slate-50 p-3
- 列ヘッダは段階名(text-sm font-semibold text-slate-700)＋件数の neutral バッジ
- 左端には未割当バックログのパネルと担当者フォーカストレイが別途ある
- カードは、上段にタイトル(2行でクランプ)と右に優先度バッジ、下段左にステータスバッジ(と任意の進捗バー)、右に担当者イニシャルの丸
- ドラッグ中はドロップ先の列全体がハイライトされる
変更してほしい点:
- 完了列・中止列が常に存在するようになる。これらを通常列と見分けられるようにするか、まったく同じ見た目にするかを決めたい
- 終端列に置かれたカードからはステータスバッジが消える。空いた下段左のスペースをどう扱うか（詰める／別の情報を出す／空けたまま）
- 中止列は常時展開しておくか、折りたたみ可能にするか
検討してほしい案:
- 完了・中止列の列ヘッダの扱い（種別バッジを出す / 名前だけ / 列の枠線や背景で区別）
- 横スクロールが長くなるため、終端列を右端に固定する案も検討してよい

3) タスク一覧（/tasks）★実は一番の論点
現状:
- 各行に タイトル / 優先度バッジ / ステータスバッジ / ステータス変更のセレクトボックス / 「分割」ボタン
- 開発段階はこの画面に一切表示されていない
問題:
- 終端段階のタスクではステータスバッジとセレクトの両方を出さない。しかし開発段階も出ていないため、このままでは一覧上でそのタスクが完了なのか中止なのかを示すものが何も残らない
変更してほしい点:
- 終端段階のタスクであることが一覧で分かるようにする
検討してほしい案:
- すべての行に開発段階を出す（情報量は増えるが一貫する）
- 終端段階のタスクにだけ「完了」「中止」の印を出す（差分は最小だが例外的な作り）
- 行そのものを淡く落として終了済みであることを示す
比較のうえ推奨を1つ明示すること

4) タスク詳細モーダル（閲覧モード）
現状:
- Modal の中の先頭に、バッジが横並びで
  ステータス / 優先度 / 「開発段階: ○○」/「担当者: ○○」/「案件: ○○(必須)」
- その下に「詳細(メモ)」のブロック
変更してほしい点:
- 終端段階のタスクではステータスバッジを出さない。バッジ行が1つ減ったときの並びを確認したい
- 「開発段階: ○○」のバッジは残る。完了・中止であることが読み取れるかを確認したい

5) 完了列へのドラッグが拒否されたときの提示
- 未完了の子タスクを持つ親タスクを完了列へドラッグすると、業務ルールにより拒否される（誤操作ではなく、想定される正常な拒否）
- 拒否されるとカードは元の列へ戻る。理由を利用者に伝える必要がある
- 既存の共有 ErrorAlert（画面上部の赤系アラート）を使う想定で問題ないか、それともドラッグ操作の近くに出すべきかを検討してほしい
- 参考: 移動が成功したときは画面上部に緑系の一時メッセージ（数秒で消える）が出る既存挙動がある

情報設計の制約（要件準拠）
- 「完了」という語は、タスク全体の完了（完了種別の段階への到達）を指す場合にだけ使う。段階内の作業状態には使わない
- ステータスの選択肢は 未着手 / 作業中 / 引継待ち / 保留 の4つ。「完了」を選択肢に戻さない
- 種別を変更する UI は作らない。開発段階の新規作成フォームにも種別の選択を置かない（新規は必ず通常種別）
- 完了日時を利用者が直接編集する UI は作らない
- 誰が段階を動かせるかの権限表示は作らない
- 中止した日時を表示する UI は作らない
- 案件一覧・案件詳細・カレンダーの見た目は変更しない

出力してほしいもの
- 上記 1〜5 のモック（同一画面の状態違いはまとめて見せてよい）
- 各画面の主要コントロール一覧（ラベル文言つき）
- 採用推奨案を明示すること。とくに次の3点
  - 開発段階マスタでの種別の示し方と、終端段階の削除の扱い
  - タスク一覧で終端段階をどう示すか
  - カンバンの完了列・中止列を通常列と区別するか
- デスクトップを主とし、狭い幅での崩れ方の注意があれば短く記す

トーン
Operate モードの実用ツール。装飾より走査性。ヒーロー画像・統計・余計なマーケティング文は不要。
```

## スクリーンショットの準備（推奨）

本スペックは差分設計のため、実画面の添付が有効。デスクトップ幅で、**データが入った状態**を撮る（空状態だと密度が伝わらず、判断を誤らせる）。

| # | 画面 | 何が判断できるか | 撮影時の状態 |
|---|---|---|---|
| 1 | `/tasks` タスク一覧 | **最重要**。行の余地がどれだけあるか。終端段階の示し方を決める材料 | タスクが数件以上。長いタイトルと短いタイトルが混在。親子階層があれば含める |
| 2 | `/kanban` ボード全景 | 列の本数、横スクロールの状況、カードの密度。終端列を足す余地 | 段階が3本以上、カードが入った列と空の列の両方 |
| 3 | `/kanban/stages` 開発段階マスタ | 行のボタン列がどれだけ詰まっているか。種別表示を足す余地 | 段階が3本以上（先頭・末尾で ↑↓ が disabled になる様子も入る） |
| 4 | タスク詳細モーダル（閲覧モード） | バッジ行の折り返し具合。ステータスバッジを抜いたときの並び | 案件に紐づき担当者もいるタスク。バッジが5つ並んだ状態 |

すでに運用上「完了」という開発段階を作って使っている場合は、**その列にカードが入った状態**が写っていると判断材料として特に有効。今回の変更後の姿に最も近いため。

   - タスク一覧で終端段階をどう示すか（全行に段階を出す / 終端だけ印 / 行を落とす）

## プロンプト本文（ここからコピー）

```text
前回のモックをレビューした。土台は良いので全面刷新はしない。以下の A〜C を直し、D・E を決めたい。

そのまま採用する部分（変更しないでほしい）
- セクション1 開発段階マスタ: 推奨1a（終端段階にだけ種別バッジ、削除は行に残して無効化＋「この段階は削除できません」）。比較案1b/1cの不採用理由も妥当
- セクション2 カンバン: 列の骨格を通常列と同一にし、区別は列ヘッダの種別バッジのみとする判断。ドロップ先ハイライトとの衝突を理由に枠線・背景で区別しないこと、列順は段階マスタが真なので終端列を右端固定しないこと、いずれも採用する

- セクション3 タスク一覧の「全行に開発段階を出す」という方針自体は採用する（見せ方だけ A で直す）

────────────────────────
A. タスク一覧で段階バッジとステータスバッジが区別できない（最優先）

問題:
推奨3aの子タスクの行が
  子タスク [中] [未着手] [未着手] (未着手▾) 分割
となっており、段階バッジとステータスバッジが同じ意匠・同じ語で隣接している。

これは偶然ではない。開発段階の名前は利用者が自由に付けられ、「未着手」「対応中」「完了」が最も自然な命名になる。一方ステータスの語彙は 未着手・作業中・引継待ち・保留 で固定。したがって両者は日常的に同じ語になる。
本仕様は「完了という語が2つの意味を持つ状態」を解消するものなので、一覧で同じ曖昧さを作り直してはいけない。

また、詳細モーダルでは「開発段階: 完了」と接頭辞を付けているのに、一覧では素の段階名になっていて不整合。

直してほしいこと:
- 段階バッジとステータスバッジが、語が同一でも一目で別の軸だと分かるようにする
- 詳細モーダルの表記と揃える

比較してほしい案（他にあれば追加可）:
- A1: 一覧でも「段階: 対応中」のように接頭辞を付ける（モーダルと揃う。横幅は食う）
- A2: 段階バッジをピルとは別の形にする（枠線のみの角丸矩形など）。バッジの「家族」を形で分ける
- A3: 段階バッジを行内の離れた位置（右寄せなど）に置き、位置で軸を分ける

あわせて未定義の状態を1つ埋めてほしい:
- 開発段階が未設定のタスクが存在する（仕様上そういうタスクを許容しており、カンバンでは列に入らず未割り当てのバックログに置かれる）。全行に段階バッジを出す方針のとき、段階未設定の行に何を出すか。「未設定」と出す／何も出さない／プレースホルダを置く、を比較して推奨を示す

────────────────────────
B. 「引継待ち」のバッジ意匠が決まっていない

問題:
前回のモックに「引継待ち」のバッジが1つも出てこない（セレクトの選択肢にあるだけ）。
現行実装のステータスバッジは4種類の tone を使い分けている:
  未着手 = neutral（グレー）
  進行中（→今回「作業中」に改称） = info（青）
  完了（→今回「引継待ち」に改称） = success（緑）
  保留 = warning（黄/オレンジ）

つまり改称だけすると「引継待ち」が緑になる。一方で前回のモックは完了段階のバッジにも緑を当てている。結果として緑が「段階内の作業が終わった」と「タスク全体が完了した」の二義を持ち、今回消したい構図が色の層で再現してしまう。

直してほしいこと:
- 緑は「タスク全体の完了（完了段階）」に予約する
- そのうえで「引継待ち」に何色を割り当てるか決める。引継待ちは「この段階の作業は終わり、次の担当者が引き取れる」という、次のアクションを促す状態であることを踏まえる
- 既存4tone（neutral/info/success/warning）の再割り当てで収めるか、新しい tone を1つ増やすかも判断して推奨を示す
- 決めた配色で、ステータス4種（未着手・作業中・引継待ち・保留）が並んだ見本を出す
- さらに、その配色で タスク一覧の行 / カンバンのカード / 詳細モーダルのバッジ行 がどう見えるかを1つずつ示す（引継待ちのタスクを必ず含める）

────────────────────────
C. 拒否バナーの文言が仕様と合っていない

前回の文言:
「未完了の子タスクが1件あるため完了にできません。先に子タスクを完了してください。」

2点ずれている:
- 仕様では、子タスクを「中止」しても親は完了できる。「完了してください」だけだと中止という出口が案内されない
```
