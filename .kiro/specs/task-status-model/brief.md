# Brief: task-status-model

## Problem

タスクの「ステータス」と「開発段階」に、性質の異なる 2 つの軸が混ざっている。

- 軸1: どの工程にいるか（開発段階／カンバンの列）
- 軸2: その工程内での作業状態（未実施 → 実装中 → 完了）
- 軸3: タスク全体が終わったか（システムが消化数集計に必要とするもの）

想定している運用フロー（要求仕様の段階で未実施→実装中→完了、次に設計の段階へ移して再び未実施から…）では、軸2の「完了」が軸3の「完了」として打刻されてしまう。段階を進めてステータスを未実施に戻した時点で `completedAt` が null に戻るため、消化数に現れるのは「今まさに完了で止まっているタスク」だけになり、集計として機能しない。

運用でカバーする（「完了」という開発段階を作り、終わったタスクをそこに置く）ことは可能だが、それは規約でありシステムが理解できないため、消化数の自動集計には使えない。

## Current State

- `Task.status` は `TaskStatus` enum（`not_started` / `in_progress` / `done` / `on_hold`）で、開発段階とは独立
- カンバンの列は開発段階（`Task.developmentStageId`）であり、ドラッグで段階が変わる（`frontend/pages/kanban/index.vue`）
- `completedAt` は `status === "done"` のとき打刻し、それ以外では null に戻す（`backend/src/modules/tasks/task.service.ts:55`）
- 消化数は `completedAt` の期間フィルタのみで算出する（`backend/src/modules/throughput/throughput.repository.ts:15`）
- 親子完了制約（子が未完了なら親を完了にできない）は `status = done` への遷移時にチェックしている（`backend/src/modules/tasks/task.service.ts:49`）
- `DevelopmentStage` は `name` と `order` のみを持ち、終端かどうかを表す属性はない

## Desired Outcome

- タスク全体の完了を、開発段階の到達によってシステムが判定できる
- 段階内の作業状態と、タスク全体の完了が、用語レベルでも混同されない
- 消化数が「期間内に本当に終わったタスク」を数えられる
- 中止したタスクを消化数から除外できる

## Approach

採用方針（検討済み・決定事項）:

- **終端ステージ方式**を採る。`DevelopmentStage` に種別（通常 / 完了 / 中止）を持たせ、完了種別の段階へタスクが入った時刻を `completedAt` とする。段階から出た場合は打刻を解除する
- **`status` は段階内の作業状態に意味を限定する**。値は「未着手 / 作業中 / 引継待ち / 保留」とし、従来の `done` は「そのタスクが終わった」ではなく「この段階の作業は終わり、次の担当者が引き取れる」を意味する `引継待ち` へ改称する
- 段階遷移の履歴そのものは task-detail の操作ログが記録するため、本仕様では履歴モデルを新設しない。段階別リードタイム分析が必要になった場合は操作ログを遡る

検討して見送った案:

- ステータスを廃し開発段階だけで進捗を表す案: 「実装段階に置かれているがまだ着手していない」が表現できず、未アサインプールと WIP 制限付き個人レーンを区別する現行運用と相性が悪い
- 段階遷移履歴を正としてそこから完了を導出する案: 段階別リードタイム分析には強いが、単体では機構が重い。履歴は task-detail の操作ログで得られるため現時点では不要

## Scope

- In
  - 開発段階への種別（通常 / 完了 / 中止）の追加と、その管理 UI（開発段階設定画面）
  - `completedAt` の打刻責務を、ステータス変更から完了種別の段階への移動へ移す
  - `TaskStatus` の値の再定義と改称（`done` → `引継待ち`）
  - 親子完了制約のチェック位置の移動
  - 消化数集計が新しい完了定義に追従すること（中止種別の除外を含む）
  - カンバン・タスク詳細モーダル等、ステータス表示箇所の用語追従
- Out
  - 段階別リードタイム／サイクルタイムの分析・可視化
  - ストーリーポイントと消化ペース予測（velocity-dashboard）
  - ステータスや段階に対する権限制御（誰が動かせるか）
  - 段階遷移のワークフロー強制（順序スキップの禁止など）
  - 段階遷移をトリガーとする通知

## Boundary Candidates

- 完了判定と `completedAt` 打刻の移動
- ステータス値の再定義と表示の追従
- 消化数集計の追従

## Out of Boundary

## Constraints

- 本番データがないため、スキーマ変更はマイグレーション削除＋DB リセットで対応する
- `.kiro/steering/product.md` の記述（「状態変更(未着手/進行中/完了/保留)」「子タスクが未完了のまま親を完了にはできない」）の更新が必要
- 画面変更を含むため `.kiro/steering/ui-design.md` の claude design ゲート対象

## Resolved Decisions

### 開発段階の種別

- 完了種別・中止種別の開発段階は、それぞれ常に 1 つだけ存在する
- 両者は必ず存在し、削除できない
- 開発段階の設定自体は任意であり、段階未設定のタスクを完了・中止へ直接移す運用も成り立つ
- 既存 DB の開発段階データは移行対象とせず、データ削除で対応する

### 「完了」と「クローズ」の区別

タスク全体の状態には、性質の異なる 2 つの判定がある。

- **完了**: 完了種別の段階に到達したもの。消化数が数える対象
- **クローズ**: 完了または中止の段階に到達し、もう作業しないもの。親子完了制約と案件進捗が見る対象

中止は「クローズ済みだが未消化」として扱う。中止を単なる未完了として放置すると、親タスクと案件を永久に閉じられなくなるため、この区別が必要になる。

### 中止タスクの扱い

- `completedAt` は打刻しない（消化数に含めない）
- 親タスクの完了を阻まない（中止した子はクローズ済みとみなす）
- 案件の必須タスク進捗では分母から外す（必須 5 件中 1 件中止なら「4 件中 3 件完了」）
- 案件終了日超過の警告対象にしない
- 中止日時の専用列は設けず、クローズ判定は今いる段階の種別から導出する。中止した日時が必要な場合は task-detail の操作ログを辿る

### ステータスの扱い

- 開発段階を移動したとき、`status` は「未着手」へリセットする
- 終端段階（完了・中止）では `status` を表示・編集させない。終端段階には段階内の作業が存在しないため、ステータスという概念が適用されない
- `status` に「完了」は復活させない。段階と `status` の両方に「完了」が併存すると、本仕様が解消しようとしている二重の意味が戻るため
