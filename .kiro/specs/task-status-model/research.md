# Gap Analysis: task-status-model

実施日: 2026-08-09 / 対象: `.kiro/specs/task-status-model/requirements.md`

## 調査サマリ

- 完了を判定しているコードは **`status === "done"` を参照する 5 箇所**に集中しており、いずれも浅い変更で済む。アーキテクチャ変更は不要
- 一方で「完了」の意味を段階種別へ移すと、**tasks・cases・throughput の 3 モジュールが同じ「クローズ済み判定」を必要とする**。判定ロジックの重複と将来のドリフトが最大の設計論点
- 消化数（Requirement 7）は **現状実装のままで大半が充足される**。中止タスクは完了日時が打たれないため、明示的な除外フィルタが不要
- 開発段階の種別を保持する仕組み（列・初期投入・一意性担保）はすべて新規。**seed 機構がリポジトリに存在しない**
- 要件側に 1 箇所穴を発見（カレンダーの期限超過判定）。後述

## 要件側で見つかった穴（Requirement 8.4 / 8.5 として反映済み）

**カレンダーの期限超過判定が要件に含まれていなかった。**

`frontend/pages/workspaces/[workspaceId]/calendar/index.helpers.ts` は `dateKey < todayIso && task.status !== "done"` で期限超過を判定している。`done` を単純にリネームすると、**完了したタスクが期限超過として赤く表示され続ける**。

当初の Requirement 8 は「ステータス語の追従」と「完了の語の一意性」しか規定しておらず、この判定基準の変更を要求していなかった。判定を「完了していない」ではなく「**クローズ済みでない**」に変える方針で、Requirement 8.4（クローズ済みは期限超過として表示しない）および 8.5（ステータスに基づいて判定しない）を追加済み。

## 実装アプローチ

### Option A: 各モジュールを個別に拡張する

`DevelopmentStage` に種別を追加し、`status === "done"` を参照している 5 箇所をそれぞれ段階種別ベースのクエリへ書き換える。

- ✅ 新規ファイルが最小。既存の feature-first 構成にそのまま収まる
- ✅ 各モジュールが自分のクエリを持つ現状の作りと一致（`caseRepository` はすでに `db.task` を直接数えている）
- ❌ **「クローズ済み」の定義が tasks・cases の 2 モジュールに重複する**。将来どちらかだけ変更されるとドリフトする
- ❌ 段階未設定（null）の扱いを各所で個別に正しく書く必要があり、抜けが生じやすい

### Option B: クローズ判定を担う新しい共有概念を切り出す

「タスクがクローズ済みか／完了済みか」を判定する責務を独立させ、各モジュールがそれを経由して判定する。

- ✅ 定義が 1 箇所に集約され、段階未設定の扱いも一元化される
- ✅ 判定基準の将来変更（例: 中止の扱いを変える）が 1 箇所で済む
- ❌ 集計クエリはデータベース側で絞り込む必要があるため、述語をどう共有するか（クエリ条件そのものを共有するのか、判定関数を共有するのか）に設計判断が要る
- ❌ steering の依存方向ルール（他モジュールへはサービスの公開インターフェース経由のみ）との整合を取る必要がある

### Option C: ハイブリッド（推奨候補）

- 段階種別そのものは `development-stages` モジュールが所有する
- 「クローズ済み／完了済み」を表すクエリ条件を `tasks` モジュールが一元的に公開し、`cases` はそれを経由して必須タスクを数える
- `throughput` は完了日時のみを見る現状の実装を維持し、新しい概念に依存させない

- ✅ 重複を避けつつ、`throughput` に不要な依存を持ち込まない
- ✅ 既存の依存方向（`cases` → 他モジュールのサービス）と整合する
- ❌ `cases` が `db.task` を直接数えている現状を、サービス経由へ寄せるかの判断が必要

## Effort & Risk

- **Effort: M（3〜7 日）** — スキーマ変更 1 件、バックエンド 4 モジュール、フロントエンド 5 ファイル程度。新しい技術要素はなく、既存パターンの範囲内。テスト更新の量が支配的
- **Risk: Medium** — 変更範囲は広いが浅い。主なリスクは 3 点
  1. `status === "done"` の参照漏れ（5 箇所は特定済みだが、テストコード内にも多数存在）
  2. 終端段階の初期投入と一意性担保の方式が未定（seed 機構が存在しない）
  3. enum リネームに伴う DB リセットで、ローカル開発環境の既存データが失われる

## Research Needed

設計フェーズへ持ち越す論点。

1. **終端段階の初期投入方式** — seed 機構がリポジトリに存在しない。マイグレーション内での投入・アプリ起動時の保証・手動作成のいずれを採るか
2. **種別の一意性担保** — 「完了種別は常に 1 つ」をどこで保証するか。MySQL は部分ユニークインデックスを持たないため、DB 制約で担保するなら既存の `templateCaseDateActiveKey`（生成列＋ユニーク制約）と同種の手法が必要。アプリケーション層のみで担保する選択肢もある
3. **種別の表現** — 列挙型（通常／完了／中止）と真偽値 2 本のいずれか
4. **クローズ済み判定の共有方式** — Option B / C の具体化。クエリ条件を共有するか、判定関数を共有するか
5. **既存テストの改修範囲** — `status` を参照するテストはバックエンド 20 ファイル・フロントエンド 6 ファイルに及ぶ。どこまでを本仕様のタスクに含めるか

## 設計フェーズへの推奨

- **Option C を起点に検討する**。重複の回避と既存の依存方向の両立が取りやすい
- **Requirement 7 は実装不要である可能性が高い**ことを設計で明示する。中止タスクが完了日時を持たないという性質から自動的に満たされるため、防御的なフィルタを足すと逆に意図が読みにくくなる
- **`countIncompleteChildren` と `countCompleted` に埋め込まれた 2 つの意図的な挙動**（ソフトデリート済みの子は親をブロックしない／ソフトデリート済みタスクは過去期間に計上し続ける）は、いずれもコード上のコメントで理由が明記されている。書き換え時に失わないこと
- 段階未設定（`developmentStageId = null`）のタスクは常に未クローズとして扱われる。この分岐を設計で明示的に定義しておく

# Design Phase: 追加調査と設計判断

実施日: 2026-08-09 / Discovery タイプ: Light（Extension）

## 追加調査の結果

| 調査項目 | 結果 |
|---|---|
| ソフトデリート拡張の適用範囲 | `withDefaultActiveFilter` は `findMany` / `findFirst` / `findUnique` / `count` の**最上位 `where` にのみ** `deletedAt: null` を注入する。リレーション経由の入れ子条件には作用しない |
| 「有効行のみ一意」の既存パターン | STORED GENERATED COLUMN ＋ UNIQUE INDEX を手編集マイグレーションで実現する方式が 2 箇所で確立（`tasks.template_case_date_active_key`、`non_business_days.date_active_key`）。Prisma スキーマでは表現できない |
| seed 機構 | **存在しない**。`backend/package.json` に seed スクリプトはなく、`prisma/` 配下も `migrations` / `schema.prisma` / テストのみ |
| `Task` ドメイン型の性質 | `export type { Task } from "@prisma/client"` の再エクスポート。API ペイロードに導出値を足すとこの規約から外れる |

## Design Decisions

### 1. クローズ判定を単一ファイルへ集約する（Generalization）

Requirement 3・5・6・8 はいずれも「このタスクはもう動かないか」という同一の問いの変種である。個別に条件を書くと定義が 4 箇所へ分散する。`tasks` モジュール内の `task.closure.ts` に述語を集約し、`cases` もこれを参照する。

`structure.md` の「他モジュールへはサービス公開インターフェース経由」から外れるため、design.md に例外として根拠を明記した。代替案（`tasksService` に案件向け集計メソッドを置く）は、案件進捗という `cases` 固有の意味を `tasks` へ持ち込むため採らない。

### 2. データベース制約による不変条件の担保を見送る（Simplification / 利用者確認済み）

「完了・中止はそれぞれ 1 つ」は、初期投入・作成時の種別固定・種別変更経路の不在・削除の拒否という 4 つの仕組みで既に維持される。生成列＋一意インデックスによる二重の担保は、3 本目の手編集マイグレーションを要し、後述の `migrate dev` の罠を増やす。

**利用者確認**: 「フロントおよび API で担保できているなら DB 側の制約は不要」との判断を得た（2026-08-09）。

**残存リスク**: 直接 SQL を実行した場合は不変条件が破れうる。運用上は許容する。

### 3. 手書きの追加マイグレーションを `migrate deploy` で適用する

通常の運用は「本番データがないため、手書き RENAME SQL を避けてマイグレーション削除＋DB リセット」である。本件ではこれが使えない。

`TaskStatus` の改名対象である `tasks` テーブルは、Prisma スキーマ言語で表現できない STORED GENERATED COLUMN と UNIQUE INDEX（`template_case_date_active_key`）を持つ。`.kiro/steering/local-dev-pitfalls.md` の項目 6 に記録済みのとおり、この状態で `prisma migrate dev` を実行すると Prisma が生成列を drift と誤検知して **DROP する追従マイグレーションを自動生成する**。

**確認事実**: `schema.prisma` の `@@unique` 宣言は `@@unique([workspaceId, userId])` の 1 件のみで、2 つの生成列（`tasks.template_case_date_active_key`、`non_business_days.date_active_key`）に対する一意制約は宣言されていない。したがって再生成による復元は不可能で、繰り返しタスクの重複防止と非営業日の日付一意性が失われる。

steering の指示どおり、手書きマイグレーションを `prisma migrate deploy` で適用する。当初「標準運用から外れる」と記述したが、正しくは **steering に記録済みの回避手順に従う**であり、design.md の記述を訂正した。

### 4. 段階の種別を API ペイロードへ含めない（Build vs. Adopt の判断）

フロントエンドのクローズ判定には段階の種別が要る。`Task` ペイロードに `developmentStageKind` を足す案は、`Task` が Prisma モデルの再エクスポートである規約を崩し、`tasks` モジュール全体に影響する。既に第一級の API である `GET /api/development-stages` の結果とクライアント側で突き合わせる方式を採り、判定は `useTaskClosure` に集約する。

**代償**: `calendar` と `cases` の 2 画面で段階一覧の取得が増える。一覧は小さく、カンバンと同じ取得方法のため影響は限定的。

### 5. Requirement 7 に実装を伴わせない（Simplification）

消化数の 4 条件はすべて、既存実装と打刻規則の組み合わせで自動的に成立する。防御的フィルタを足すと「中止は完了日時を持たない」という不変条件が二重表現になり、意図が読みにくくなる。**フィルタではなくテストで固定する**。

### 6. 新しい通常段階の挿入位置を変更する

現在の `create` は `max(order) + 1`。完了・中止が末尾に常駐するため、そのままだと新しい通常段階が終端段階の後ろに並び、毎回の並び替えを強いる。通常種別の最大 `order` の直後へ挿入する挙動に変更する。Requirement 1.7（終端段階の並び替えを許可）とは独立に成立する。

### 主要な設計判断と根拠

- **段階とステータスを形で分ける**: 段階名は利用者が自由に命名でき「未着手」「対応中」がステータス語彙と日常的に衝突する。接頭辞のみでは意匠が同じで遠目に区別できず、形のみでは意味の学習が要る。併用で両方を解消する
- **引継待ちに新 tone を足す**: warning への再割り当ては同じ行に並ぶ優先度「中」（`#fef9c3`）と実質同色になり軸を取り違える。濃い青は primary を状態色へ転用することになる。緑は完了段階に予約する
- **中止は取り消し線**: 色に依存しないため色覚特性に左右されず、段階名を改名しても印が名前に追従する。赤や警告色を使わないので「中止は失敗ではない」という性質に合う。完了の緑とは色ではなく線の有無で対比する。破線案は未設定バッジと記号を共有するため不採用、濃いグレー案は「強調」に見えて静かにしていてほしい行が目立つため次点
- **進捗の補足行**: 「1/2」だけでは、子が 3 件見えているのに分母が 2 になる理由がカード上のどこにも書かれない。分母が黙って変わるのは進捗を疑わせる。ツールチップはドラッグ操作と競合し、タッチでは開けないため不採用
- **中止列の折りたたみを入れない**: (1) 要件外の状態が増える (2) 保存先の決定が要る (3) 畳んだままだとドラッグ先が消える、の 3 つの負債に対し「縦が短くなる」だけの効果では釣り合わない

## 設計レビューでの指摘と反映（2026-08-09）

`/kiro-validate-design` で 3 件を検出し、design.md へ反映した。

### 1. マイグレーションが既存行を不変条件へ整合させていなかった

追加マイグレーション方式は既存行を残すため、旧 `done` のタスクが `completed_at` を保持したまま完了段階の外に置かれる。`throughputRepository.countCompleted` は `completed_at` のみを見るため、**本仕様が是正しようとしている消化数が誤ったままになる**という、目的を損なう欠陥だった。

→ マイグレーション末尾に整合処理を追加。旧 `done` のタスクを完了段階へ移し、`completed_at` を保持し、`status` を `not_started` にリセットする。消化数の履歴を失わない形を選んだ。

### 2. カンバンのドラッグに生まれる新しい業務エラー経路が未考慮だった

`incomplete_children` の発生契機がステータス変更から**開発段階の変更**へ移る結果、カンバンのドラッグで正常に発生しうる拒否になる。`onDropOnStage` は例外処理を持たず、楽観更新の巻き戻しも通知もされない状態だった。

→ `pages/workspaces/[workspaceId]/kanban/index.vue` を File Structure Plan と Modified Files に追加し、同一ファイル内の `handleFocusTrayAssign` が持つ既存の復旧パターン（`revertOptimisticMove()` ＋ 共有 `ErrorAlert`）を踏襲することを明記した。新しい復旧機構は設けない。

### 3. Requirement 4.5 の適用範囲と影響画面数の誤り

`TaskNode.vue` はステータスのバッジと編集セレクトの両方を描画するため 4.5 の対象だが、コンポーネント表では 8.2 のみを割り当てていた。あわせて段階一覧の取得が増える画面を「2 画面」と記載していたが、当時は `calendar`・`cases`・`tasks` の 3 画面が正しい、として訂正した。

→ 双方を訂正。E2E にタスク一覧での非表示確認を追加した。
| 既存テストの改修漏れ | 判定基準の変更が検証されないまま残る | `task.service.test.ts` / `case.service.test.ts` は機械的置換では済まないことを明記 |

## main マージ後の文書同期（2026-08-12）

`workspace-url-routing` が main に入り、業務画面は `frontend/pages/workspaces/[workspaceId]/...` 配下・URL は `/workspaces/:workspaceId/...` になった。あわせて `DevelopmentStage.workspaceId` 前提で、終端段階の不変条件を「グローバルに各 1 つ」から「各ワークスペースで各 1 つ」へ言い直した。

| 項目 | 同期後の正 |
|---|---|
| フロントパス | `pages/workspaces/[workspaceId]/{kanban,calendar,tasks,cases}/...` |
| 画面 URL | `/workspaces/:workspaceId/{kanban,tasks,...}` |
| 要件 1.2 / 1.3 | 各ワークスペースで完了・中止がちょうど 1 つ |
| マイグレーション初期投入 | 既存各 WS へ完了・中止を投入（固定 UUID 1 組ではない） |
| seed | 新規 WS を作るため、当該 WS 向けに終端段階を種別つきでちょうど 1 つずつ作る |
| 既存マイグレーション本数 | 4 本（本仕様で手書き 1 本を追加） |
| 段階一覧の取得追加 | `cases`・`tasks` のみ（`kanban`・`calendar` は取得済み） |

詳細は `design.md` / `requirements.md` / `tasks.md` を正とする。冒頭の gap 分析の「5 箇所」「seed なし」は歴史的記述であり、後続の訂正セクションと本節が優先する。
