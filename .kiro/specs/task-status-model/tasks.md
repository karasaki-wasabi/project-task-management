# Implementation Plan

- [ ] 1. 基盤: スキーマ・初期投入・クローズ判定
- [x] 1.1 開発段階の種別と新しいステータス値をスキーマへ反映し、マイグレーションを適用する
  - 開発段階に通常・完了・中止の種別を持たせ、ステータスの列挙値を新しい語彙へ改称する
  - 中止した日時を保持する列は追加しない
  - マイグレーション SQL は手書きし、既存の各ワークスペースに完了・中止の段階を投入する（グローバルな固定識別子 1 組では投入しない）
  - 旧「完了」ステータスのタスクを、当該ワークスペースの完了段階へ移し、完了日時を保持したままステータスを未着手へ戻す
  - スキーマ言語で表現できない生成列と一意インデックスが失われるため、差分生成を伴う適用手段は使わず、手書き SQL をそのまま適用する。その理由を SQL 冒頭にコメントで残す
  - 観測可能: 適用後、各ワークスペースで完了種別・中止種別の段階がそれぞれ 1 件だけ存在し、完了日時を持つタスクがすべて当該ワークスペースの完了段階に属する
  - _Requirements: 1.1, 1.2, 1.3, 3.4, 4.1_

- [x] 1.2 シードデータを新しい段階種別へ追従させる
  - シードは新規ワークスペースを作るため、当該ワークスペース向けに完了・中止段階を種別つきでちょうど 1 つずつ作成する
  - シードが作るタスクのステータス値を新しい語彙へ置き換え、完了済みとして置くタスクは当該ワークスペースの完了段階へ紐づける
  - 観測可能: シードを実行しても、当該ワークスペースで完了種別の段階は 1 件のままで、種別の不変条件が破れない
  - _Depends: 1.1_
  - _Requirements: 1.2, 1.3, 4.1_

- [x] 1.3 タスクのクローズ判定を単一の定義として切り出す
  - 完了済み・クローズ済み・未クローズを判別する述語を、タスク領域に 1 箇所だけ用意する
  - 判定は現在置かれている開発段階の種別から導出し、開発段階が未設定のタスクは常に未クローズとして扱う
  - 観測可能: 未クローズとクローズ済みの述語が互いに補集合になり、段階未設定のタスクが未クローズ側にのみ一致することを単体テストで確認できる
  - _Depends: 1.1_
  - _Requirements: 3.1, 3.2, 3.3_

- [ ] 2. 開発段階の種別の強制
- [ ] 2.1 段階の種別を読み取れるようにする
  - ドメイン型と一覧取得の応答に種別を含める
  - 単一の段階を識別子から取得する手段を用意する（タスク側が遷移先の種別を解決するために必要）
  - 観測可能: 段階一覧の取得結果に各段階の種別が含まれる
  - _Depends: 1.1_
  - _Requirements: 1.1, 1.8_

- [ ] 2.2 種別の不変条件を操作側で守る
  - 新規作成は常に通常種別とし、通常段階の末尾へ挿入して終端段階の後ろへ回り込まないようにする
  - 終端種別の段階の削除を拒否する
  - 名称変更と並び替えは終端段階でも許可し、種別を変更する経路は設けない
  - 観測可能: 終端段階の削除要求が拒否され、新規作成した段階が必ず通常種別になる
  - _Requirements: 1.4, 1.5, 1.6, 1.7_

- [ ] 3. 完了判定とタスクの制約
- [ ] 3.1 開発段階の変更に完了日時・ステータス・親子制約を集約する
  - 完了種別の段階へ移した時刻を完了日時として記録し、他の段階へ移した場合は記録を解除する
  - 中止種別の段階へ移した場合は完了日時を記録しない
  - 段階が実際に変わった場合にかぎり、ステータスを未着手へ戻す
  - 完了種別の段階へ移す場合にかぎり未クローズの子タスクの有無を確認して拒否する。中止種別への移動は子の状態にかかわらず許可する
  - 開発段階が未設定のタスクを終端段階へ直接移せる状態を保つ
  - 観測可能: 完了段階へ移すと完了日時が入り、通常段階へ戻すと消え、再度移すと打ち直される
  - _Depends: 1.3, 2.1_
  - _Requirements: 2.1, 2.2, 2.3, 2.5, 4.4, 5.1, 5.2, 5.3, 5.4_

- [ ] 3.2 ステータス変更を段階内の作業状態に限定する
  - ステータス変更から完了日時の打刻と親子制約の判定を取り除く
  - 終端段階にあるタスクのステータス変更を拒否する
  - 完了日時を直接編集できる経路がないことを保つ
  - 観測可能: ステータスを変えても完了日時が変化せず、終端段階のタスクへのステータス変更が拒否される
  - _Depends: 3.1_
  - _Requirements: 2.4, 2.6, 4.2, 4.3, 4.5_

- [ ] 3.3 クローズ済みのタスクに未クローズの子が付かないようにする
  - クローズ済みのタスクの分割を拒否する
  - 未クローズのタスクの親としてクローズ済みのタスクを指定する操作を拒否する
  - 観測可能: 完了段階のタスクの分割要求と、完了段階のタスクを親に指定する要求がいずれも拒否される
  - _Depends: 1.3_
  - _Requirements: 5.5, 5.6_

- [ ] 3.4 (P) 案件の必須タスク進捗をクローズ基準へ移す
  - 完了種別の段階にある必須タスクを完了件数として数える
  - 中止種別の段階にある必須タスクを集計の母数から除外する
  - 母数が 0 になる場合は進捗を提示しない
  - 観測可能: 必須タスク 5 件のうち 1 件を中止すると母数が 4 になり、案件終了日を過ぎた際の警告も中止分を対象にしない
  - _Depends: 1.3_
  - _Boundary: caseRepository, CaseService_
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5, 6.6_

- [ ] 4. 表示基盤の整備
- [ ] 4.1 クライアントの型定義とステータスバッジを新しい語彙へ揃える
  - API クライアントが扱うステータス値を新しい語彙へ更新し、開発段階の型に種別を加える
  - ステータスのラベルを 未着手・作業中・引継待ち・保留 に更新する
  - 引継待ち専用の配色を追加し、緑をステータスから外して完了段階に予約する
  - 観測可能: 4 種のステータスが互いに区別でき、緑がステータスの表示に現れない
  - _Depends: 2.1_
  - _Requirements: 8.2, 8.3_

- [ ] 4.2 (P) 開発段階バッジを新設する
  - 枠線つきの角丸矩形に接頭辞を添える意匠とし、通常・完了・中止・未設定の 4 状態を表現する
  - 中止は段階名にのみ取り消し線を掛け、接頭辞には掛けない
  - 一覧とモーダルで接頭辞の語を変えつつ、意匠は共通に保つ
  - 観測可能: 段階名がステータスと同じ語になっても、形と接頭辞で 2 つの軸が区別できる
  - _Depends: 4.1_
  - _Boundary: StageBadge_
  - _Requirements: 8.2, 8.3_

- [ ] 4.3 (P) クライアント側のクローズ判定を用意する
  - 段階一覧とタスクからクローズ状態を求める純粋関数を 1 箇所に置く
  - 段階が未設定の場合と、一覧に存在しない段階を指している場合は、いずれも未クローズとして扱う
  - 観測可能: 段階未設定のタスクと未知の段階を指すタスクが、どちらも未クローズと判定されることを単体テストで確認できる
  - _Depends: 4.1_
  - _Boundary: useTaskClosure_
  - _Requirements: 8.4, 8.5_

- [ ] 5. 画面の追従
- [ ] 5.1 開発段階マスタ画面に種別を反映する
  - 終端段階にだけ種別を示し、通常段階は無印にする
  - 終端段階の削除操作を無効化し、削除できない理由を添える
  - 名称変更と並び替えは終端段階でも操作できる状態を保つ
  - 観測可能: 完了・中止の行で削除が押せず、その理由が画面上で読める

  - _Boundary: frontend/pages/workspaces/[workspaceId]/kanban/stages.vue_
  - _Requirements: 1.5, 1.8_

- [ ] 5.2 (P) タスク一覧に段階を出し、操作列の位置を固定する
  - すべての行に段階を示し、段階が未設定の行にもその旨を示す
  - 終端段階の行ではステータスの表示・選択と分割操作を出さない
  - 行を「タイトルとバッジ群／余白／操作群」に分け、バッジの増減で操作の位置が動かないようにする
  - 観測可能: 終端段階の行でも操作群の位置が他の行と揃う

  - _Boundary: TaskNode_

- [ ] 5.3 (P) タスク詳細モーダルを追従させる
  - 段階の表示を新しいバッジへ置き換える
  - 終端段階のタスクではステータスを表示しない
  - 観測可能: 終端段階のタスクでバッジが 1 つ減っても、段階の表示位置が動かない
  - _Depends: 4.2, 4.3_
  - _Boundary: TaskDetailModal_
  - _Requirements: 4.5, 8.2_

- [ ] 5.4 (P) カンバンの集計をクローズ基準へ移す
  - 子タスク進捗を「完了段階の子の数 ÷ 中止段階の子を除いた数」で数え、除外した件数を表示側へ渡せるようにする
  - 母数が 0 になる場合は進捗を算出しない
  - 担当者フォーカストレイとチーム負荷の集計からクローズ済みのタスクを除く
  - 観測可能: 子 3 件のうち 1 件完了・1 件中止・1 件未完了の親で、進捗が 2 件中 1 件として算出される

- [ ] 5.5 カンバンのカード表示を追従させる

  - 中止した子がいる親では、進捗の脇に中止分を除いている旨を添える
  - 終端列と母数 0 の場合は進捗そのものを出さない

  - 母数が 0 の場合に進捗を提示しない
  - 観測可能: 完了段階の必須タスクに完了の印が付き、中止した必須タスクが未完了として残らない

- [ ] 6. 統合
- [ ] 6.1 カンバンでの段階変更の拒否を復旧と提示につなぐ
  - 完了列への移動が業務ルールで拒否されうるようになるため、失敗時に楽観的に更新された配置を元へ戻す
  - 拒否の理由を既存の共有アラートで提示し、自動では消さず閉じるまで残す
  - 成功時の一時メッセージは従来どおり数秒で消える挙動を保つ
  - 観測可能: 未クローズの子を持つ親を完了列へドラッグすると、カードが元の列へ戻り、理由が画面上に残る
  - _Depends: 3.1, 5.5_
  - _Boundary: frontend/pages/workspaces/[workspaceId]/kanban/index.vue_
  - _Requirements: 5.1_

- [ ] 7. 検証
- [ ] 7.1 完了判定と消化数の非回帰を検証する
  - 完了段階への出入りで消化数の集計対象が変わることを確認する
  - 中止したタスクが消化数に現れないことを確認する。これは除外条件ではなく打刻規則によって成立するため、防御的なフィルタを足さずにテストで固定する
  - 論理削除済みのタスクが過去期間の集計に残り続ける既存の挙動が保たれていることを確認する
  - 観測可能: 期間集計のテストが、完了段階の出入りと中止の双方で期待どおりの件数を返す
  - _Depends: 3.1_
  - _Requirements: 7.1, 7.2, 7.3, 7.4_

- [ ] 7.2 親子とクローズの制約を検証する
  - 未クローズの子を持つ親の完了が拒否され、その子を中止すると親を完了にできることを確認する
  - 親の中止が子の状態にかかわらず許可されることを確認する
  - クローズ済みのタスクの分割と、クローズ済みのタスクを親に指定する操作が拒否されることを確認する
  - 論理削除済みの子が親の完了を妨げない既存の挙動が保たれていることを確認する
  - 観測可能: 上記の遷移と拒否がすべてテストで固定される
  - _Depends: 3.1, 3.3_
  - _Requirements: 5.1, 5.2, 5.3, 5.5, 5.6_

- [ ] 7.3 画面の主要動線を E2E で確認する
  - カンバンに完了列と中止列が他の列と同様に表示されることを確認する
  - カードを完了列へ移すと消化数の画面に反映されることを確認する
  - 終端列のカードと、タスク一覧の終端段階の行で、ステータスが表示されないことを確認する
  - 期限を過ぎた完了済み・中止済みのタスクがカレンダーで期限超過にならないことを確認する
  - 開発段階マスタで終端段階の削除操作が押せないことを確認する
  - 観測可能: 上記の経路がすべて E2E で通る
  - _Depends: 5.1, 5.2, 5.5, 5.7, 6.1_
  - _Requirements: 1.5, 1.8, 2.1, 4.5, 7.1, 8.1, 8.4, 8.10_
