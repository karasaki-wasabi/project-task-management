# Requirements Document

## Project Description (Input)

利用者および今後ワークスペース・コメント・操作ログを使うチームは、現状どの API／画面も認証なしで触れられ、「誰が操作しているか」をサーバが保証できない。`User` は名前だけの担当者レコードであり、ログイン・パスワード・セッションはない。本仕様では `User` をアカウントへ拡張し、公開自己登録とセッションによるログイン／ログアウト、要ログインの API／画面ガードを導入する。ワークスペース・RBAC・JWT は対象外とする。登録識別子は一意なメールアドレスとし、あわせて表示名を持つ。

## Introduction

本スペックは、名前だけの担当者レコードであったユーザーを、メールアドレスとパスワードで自己登録できるアカウントへ拡張する。公開の登録・ログインを提供し、ログイン後はセッションにより操作主体を特定する。登録・ログイン以外の画面と業務 API は未ログインでは利用できないようにする。ログイン済みユーザー同士に権限差は設けない。ワークスペースによるデータの見える範囲の分離、招待リンク、メール送信、外部 IdP、JWT／機械向けトークンは後続仕様の対象とする。

## Boundary Context

- In scope
  - メールアドレス（一意）・表示名・パスワードによる公開自己登録
  - ログイン・ログアウト、およびログイン状態の維持
  - 未ログイン時の業務画面・業務 API 利用の拒否
  - 名前だけのユーザー登録 UI／操作の廃止と、登録済みアカウントを担当者候補として選べることの維持
  - 認証あり前提へのプロダクト説明（steering）の更新
- Out of scope
  - ワークスペースの作成・所属・招待
  - 案件・タスク等のデータスコープ分離
  - ロールや操作単位の細かい権限（RBAC）
  - 招待リンク、メール送信（確認メール・パスワード再設定メールを含む）、OAuth／外部 IdP
  - JWT および MCP 等向けの機械用トークン
  - 他ユーザーのアカウント削除、パスワード再設定フロー
- Adjacent expectations
  - タスク・カンバン・カレンダー等の担当者選択／絞り込みは、従来どおり登録済みユーザー一覧を候補とする。候補の供給源は「名前だけ登録」から「自己登録されたアカウント」へ切り替わる
  - ワークスペース導入後は担当者候補を同一ワークスペースのメンバーに限定する想定だが、その変更は本スペックの対象外とする
  - 既存データは破棄前提とし、名前だけユーザーからアカウントへの移行ツールは提供しない

## Requirements

### Requirement 1: アカウントの自己登録
**Objective:** As a これから本システムを使い始める利用者, I want メールアドレスと表示名とパスワードで自分のアカウントを登録できる, so that ログイン可能な操作主体としてシステムを利用し始められる

#### Acceptance Criteria
1. When 未ログインの利用者が登録操作を行う, the タスク管理システム shall メールアドレス・表示名・パスワードを入力してアカウントを作成できる登録手段を提供する。
2. The タスク管理システム shall 登録済みアカウントごとに一意なメールアドレスと、空でない表示名を保持する。
3. If メールアドレスが未入力、形式として不正、または既に登録済みである状態で登録が実行される, then the タスク管理システム shall アカウントを作成せず、登録できない旨を利用者に示す。
4. If 表示名が未入力（空白のみを含む）の状態で登録が実行される, then the タスク管理システム shall アカウントを作成せず、登録できない旨を利用者に示す。
5. If パスワードが未入力、または8文字未満である状態で登録が実行される, then the タスク管理システム shall アカウントを作成せず、登録できない旨を利用者に示す。
6. When 登録が成功する, the タスク管理システム shall パスワードを画面上や応答の確認可能な項目として表示しない。
7. When 登録が成功する, the タスク管理システム shall 利用者が続けてログインして業務画面を利用できる状態にする。

### Requirement 2: ログイン・ログアウトとセッション
**Objective:** As a 登録済み利用者, I want ログインして作業し、ログアウトで利用を終えられる, so that 自分の操作としてシステムを使え、終了後は他人に使われ続けない

#### Acceptance Criteria
1. When 登録済み利用者が正しいメールアドレスとパスワードでログイン操作を行う, the タスク管理システム shall その利用者をログイン状態にし、業務画面を利用可能にする。
2. If メールアドレスまたはパスワードが誤っている状態でログイン操作が行われる, then the タスク管理システム shall ログイン状態にせず、認証に失敗した旨を利用者に示す。
3. While 利用者がログイン状態である, the タスク管理システム shall ブラウザを閉じずに同一クライアントで操作を続ける間、明示的な再ログインなしでログイン状態を維持する。
4. When ログイン中の利用者がログアウト操作を行う, the タスク管理システム shall ログイン状態を終了し、以降の業務画面・業務 API を未ログインとして扱う。
5. The タスク管理システム shall ログイン応答や画面表示においてパスワードを露出しない。

### Requirement 3: 未ログイン時の保護
**Objective:** As a システムの運用者および利用者, I want ログインしていない相手が業務機能を使えない, so that 操作主体が不明なままデータが操作されない

#### Acceptance Criteria
1. The タスク管理システム shall アカウント登録とログインに必要な画面を、未ログインのまま利用できるようにする。
2. If 未ログインの利用者が業務画面（登録・ログイン以外）へアクセスしようとする, then the タスク管理システム shall 業務内容を見せず、ログインが必要な状態へ導く。
3. If 未ログインの利用者が業務 API（登録・ログインに必要なものを除く）を呼び出そうとする, then the タスク管理システム shall その操作を拒否する。
4. When ログイン状態が終了したあとで業務画面や業務 API を利用しようとする, the タスク管理システム shall 未ログイン時と同様に拒否またはログインへ導く。

### Requirement 4: 名前だけユーザー管理の置換と担当者候補
**Objective:** As a ログイン済み利用者, I want 名前だけのユーザー登録ではなくアカウントとしてユーザーが管理され、担当者選択は従来どおり使える, so that 認証導入後もタスクの担当付けができる

#### Acceptance Criteria
1. The タスク管理システム shall 名前だけを入力してユーザーを登録する従来の手段を提供しない。
2. When ログイン済み利用者が担当者の候補一覧を参照する, the タスク管理システム shall 自己登録されたアカウントを表示名で候補として提示できる。
3. The タスク管理システム shall ログイン済み利用者同士のあいだで、他者のアカウントを削除する手段を提供しない。
4. Where 既存画面が担当者の選択または担当者による絞り込みを提供している, the タスク管理システム shall それらの画面が登録済みアカウントを候補として利用し続けられるようにする。

### Requirement 5: ログイン済みユーザーの権限の対等
**Objective:** As a ログイン済み利用者, I want 他のログイン済み利用者と同じ利用権限である, so that 本仕様の範囲では役割による操作差を気にせず使える

#### Acceptance Criteria
1. The タスク管理システム shall ログイン済みである利用者に対し、本仕様の範囲で管理者と一般のような操作権限の差を設けない。
2. The タスク管理システム shall ロールの割り当てや権限マトリクスの設定手段を提供しない。

### Requirement 6: 認証まわりの誤り表示
**Objective:** As a 利用者, I want 登録やログインに失敗したとき理由が分かること, so that 入力を直して再試行できる

#### Acceptance Criteria
1. If 登録またはログインが入力不備や認証失敗により完了しない, then the タスク管理システム shall 利用者に失敗した旨が分かる表示を行う。
2. The タスク管理システム shall ログイン失敗時に、パスワードの正誤だけを特定できるような過度に詳細な内部情報を利用者へ露出しない。

### Requirement 7: 認証前提へのプロダクト説明の更新
**Objective:** As a 本リポジトリで仕様駆動開発を進める開発者, I want 認証を持たない前提の説明が更新されている, so that 以降の仕様が古い前提と矛盾しない

#### Acceptance Criteria
1. When 本仕様が完了状態になる, the タスク管理システム shall プロダクトおよび技術の steering 説明において、認証を持たない・名前だけのユーザーのみ、という前提を、アカウント登録とログインがある前提へ更新している。
2. The タスク管理システム shall steering 上で、ワークスペース・RBAC・外部 IdP・機械用トークンがなお後続である旨を、認証導入後も混同しない形で残せるようにする。
