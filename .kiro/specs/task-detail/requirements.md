# Requirements Document

## Introduction

タスクの担当者・関係者は、タスクの確認・編集をカンバン等の詳細モーダルで行っているが、コメントや操作ログ（誰が・いつ・何をしたか）を残す場所がない。簡易な確認と、コメント／操作ログ付きの深い作業を同じ UI に詰め込むと複雑になる。本仕様は、専用のタスク詳細ページを新設し、そのタスクの CRUD、コメントの投稿・自分の投稿の編集／削除、およびタスクの作成・削除・フィールド変更とコメント操作を対象とした操作ログの記録を提供する。画面上では、コメントとフィールド変更の履歴を 1 つの時系列（タイムライン）として表示する。記録対象と表示対象は一致せず、記録が表示を包含する。既存の `TaskDetailModal` は簡易表示を基本とし、タイトル・優先度・開発段階・担当者・案件・詳細などの軽微な編集のみを残す（ステータス変更はモーダルでは提示しない）。詳細ページへの導線を追加する。操作者はログインユーザーとし、データはワークスペーススコープを前提とする。

## Boundary Context (Optional)

- **In scope**
  - タスク詳細ページの新設と、モーダルから詳細ページへの導線
  - 詳細ページ上でのタスクの閲覧・編集・削除
  - コメントの投稿・一覧表示、投稿者本人による編集・削除
  - タスクの作成・削除・フィールド変更およびコメント操作を対象とした操作ログの記録（記録対象の一覧は Requirement 5 で定義する）
  - コメントとフィールド変更履歴を 1 つの時系列で表示するタイムライン（表示対象と表示文言は Requirement 6 で定義する）
  - タスクの親子関係のつなぎ替え
  - 既存モーダルの役割整理（軽微編集は維持しつつ、詳細ページと責務が重複する表示の縮小）
  - タスクの複製
  - タイムラインの表示絞り込み（すべて／コメント／変更履歴）
  - 終了予定日超過の表示
- **Out of scope**
  - メンション通知・メール通知
  - ワークスペース横断の活動フィード
  - 細かい RBAC（コメント・操作ログの閲覧権限差など）
  - ストーリーポイント入力欄（velocity-dashboard の対象）
  - コメント・操作ログのリアルタイム更新（WebSocket 等でのプッシュ配信）
  - タスクのステータス値の定義、開発段階の種別、タスク完了の判定方法（task-status-model の対象）
- **Adjacent expectations**
  - 本仕様は「ログイン済みユーザーである」ことを前提とし、操作者の識別方法自体は規定しない（user-auth の管掌）
  - 本仕様はタスク・案件がワークスペースに属し、所属メンバーのみアクセスできることを前提とするが、その可視範囲の判定・強制自体は規定しない（workspace-resource-scope の管掌）。本仕様が定義する詳細ページの URL・アクセス制御は、workspace-resource-scope が提供する判定基盤が利用可能になっていることを前提とする
  - 案件（case）との関連付け表示・編集は既存のカンバン／詳細モーダルの挙動を踏襲し、関連付け自体の仕様（案件モデル・必須タスク判定）は case-management-ux の管掌で変更しない
  - 本仕様はタスクのステータス値・開発段階の種別・完了判定を task-status-model の管掌とし、それらを再定義しない。操作ログはステータスおよび開発段階の変更を記録するため、記録される値の語彙は task-status-model が確定させたものに従う（同仕様を本仕様より先行させる）
  - 本仕様が追加する親タスクのつなぎ替えは、task-status-model が定める不変条件「クローズ済みのタスクは未クローズの子を持たない」に従う。同制約の定義と強制は task-status-model の管掌であり、本仕様はそれに違反する操作を拒否するのみで、制約自体を再定義しない
  - フィールドの API／DB 名と表示名の揃え（`memo`→`detail`＝「詳細」、`scheduledDate`→`scheduledEndDate`＝「終了予定日」、将来の開始予定日は `scheduledStartDate`）は task-field-rename の管掌であり完了済みとする。本仕様は改名後の語彙を前提とし、マイグレーションや全画面の文言揃え自体は行わない。完了済み仕様文書（task-delivery-management 等）は更新しない運用に従う
  - 案件解除時の必須タスク自動オフ（Requirement 2.8）は既存のタスク更新 API の挙動を前提とする。本仕様が新たに定義するのは、その自動オフを操作ログへ記録することである
  - 未完了の子タスクを持つ削除（Requirement 3.3）について、既存のタスク削除 API は未完了子の有無では拒否しない（ソフトデリートする）。未完了子制約は完了種別の開発段階への移動時に適用される。本仕様は削除 API に新たな拒否条件を追加しない

## Requirements

### Requirement 1: タスク詳細ページの表示とアクセス
**Objective:** As a ワークスペースのメンバー, I want タスクの詳細を専用ページで確認できる, so that カンバンのモーダルに頼らず、タスクの全情報・コメント・操作ログをまとめて把握できる

#### Acceptance Criteria
1. When ワークスペースのメンバーが所属ワークスペース内の存在するタスクの詳細ページへアクセスした場合、the Task Detail Page shall 当該タスクの次の表示項目を表示する
   - タイトル
   - ステータス
   - 優先度
   - 詳細
   - 担当者
   - 案件関連付け（案件）
   - 必須タスクフラグ
   - 開発段階
   - 親タスク
   - 子タスク
   - 終了予定日
   - 完了日時
2. If 指定されたタスクが存在しない場合、the Task Detail Page shall タスクが見つからない旨を表示する
3. If 指定されたタスクが操作者の所属していないワークスペースに属する場合、the Task Detail Page shall タスクが存在しない場合と同じ扱いとし、リソースの有無を区別できる情報を出さない
4. While 指定されたタスクが論理削除済みである, the Task Detail Page shall 参照専用として当該タスクの表示項目とタイムラインを表示し、編集操作を提示しない
5. While 指定されたタスクの開発段階が task-status-model の定める完了種別または中止種別である, the Task Detail Page shall ステータスを表示項目から除く
6. While 指定されたタスクの終了予定日が本日より前であり、かつ当該タスクが task-status-model の定めるクローズ済みでない, the Task Detail Page shall 当該タスクを期限超過として表示する
7. The Task Detail Page shall 期限超過の判定を、タスクがクローズ済みであるかに基づいて行い、ステータスまたは完了日時の有無に基づいて行わない

### Requirement 2: タスク詳細ページでのタスク編集
**Objective:** As a ワークスペースのメンバー, I want タスク詳細ページ上でタスクの内容を編集できる, so that モーダルとページを行き来せず作業を完結できる

#### Acceptance Criteria
1. While 指定されたタスクが論理削除されていない, the Task Detail Page shall 次の項目の編集操作を提示する
   - タイトル
   - ステータス
   - 優先度
   - 詳細
   - 担当者
   - 案件関連付け（案件）
   - 必須タスクフラグ
   - 開発段階
   - 親タスク
   - 終了予定日
2. When ワークスペースのメンバーがタスク詳細ページ上でフィールドを変更して保存した場合、the Task Detail Page shall 当該タスクを更新する
3. If タスク編集時に既存のタスク作成・更新 API が定めるバリデーション（必須項目・値域など）に違反する入力が保存された場合、the Task Detail Page shall 更新を拒否しエラーを提示する
4. The Task Detail Page shall 完了日時を直接編集する操作を提示しない
5. If 親タスクの指定により循環する親子関係が生じる場合、the Task Detail Page shall 更新を拒否しエラーを提示する
6. If 親タスクとして、task-status-model が定めるクローズ済みのタスクが指定された場合、the Task Detail Page shall 更新を拒否しエラーを提示する
7. While 指定されたタスクの開発段階が task-status-model の定める完了種別または中止種別である, the Task Detail Page shall ステータスの編集操作を提示しない
8. When ワークスペースのメンバーが案件関連付けを解除した場合、the Task Detail Page shall 必須タスクフラグをオフにする
9. When ワークスペースのメンバーがタスク詳細ページでタスクの複製を実行した場合、the Task Detail Page shall 元タスクのタイトル・優先度・詳細・担当者・案件関連付け・必須タスクフラグ・親タスク・終了予定日を引き継いだ新規タスクを作成する
10. The Task Detail Page shall タスクの複製時に、ステータスおよび開発段階を初期状態で作成し、完了日時・コメント・操作ログ・子タスクの関連を引き継がない
11. When タスクの複製が完了した場合、the Task Detail Page shall 複製後の新規タスクの詳細ページへ遷移する

### Requirement 3: タスクの削除
**Objective:** As a ワークスペースのメンバー, I want 不要になったタスクをタスク詳細ページから削除できる, so that コメントや操作ログの記録を残したまま一覧から外せる

#### Acceptance Criteria
1. When ワークスペースのメンバーがタスク詳細ページでタスク削除を実行した場合、the Task Detail Page shall 当該タスクを論理削除する
2. When タスクが論理削除された場合、the Task Detail Page shall 当該タスクのコメントおよび操作ログの記録を保持する
3. If 未完了の子タスクを持つタスクの削除が試みられた場合、the Task Detail Page shall 既存のタスク削除 API が定める制約に従う（既存 API は未完了子の有無では拒否せず論理削除する。本仕様はここに新たな拒否条件を追加しない）

### Requirement 4: コメント
**Objective:** As a ワークスペースのメンバー, I want タスクにコメントを残し、自分の投稿を編集・削除できる, so that タスクに関する議論や経緯を後から追跡できる

#### Acceptance Criteria
1. When ワークスペースのメンバーがタスク詳細ページでコメント本文を入力して投稿した場合、the Comment Feature shall 投稿者・投稿日時とともにコメントを当該タスクに記録する
2. If 空文字のみのコメント本文で投稿が試みられた場合、the Comment Feature shall 投稿を拒否する
3. When コメントの投稿者本人が自身のコメントの編集を実行した場合、the Comment Feature shall 当該コメントの内容を更新し、編集済みであることを識別できるようにする
4. When コメントの投稿者本人が自身のコメントの削除を実行した場合、the Comment Feature shall 当該コメントを削除する
5. If コメントの投稿者以外のワークスペースのメンバーが当該コメントの編集または削除を試みた場合、the Comment Feature shall 拒否する

### Requirement 5: 操作ログの記録
**Objective:** As a ワークスペースのメンバー, I want タスクに対する操作が漏れなく記録される, so that 画面に表示しないものも含めて、後から誰が・いつ・何をしたかを追跡できる

#### Acceptance Criteria
1. The Activity Log Feature shall 次の操作のみを操作ログの記録対象とする
   - タスクの作成
   - タスクの削除
   - タスクのフィールド変更
     - タイトル
     - ステータス
     - 優先度
     - 詳細
     - 担当者
     - 案件関連付け（案件）
     - 必須タスクフラグ
     - 開発段階
     - 親タスク
     - 終了予定日
   - コメントの投稿・編集・削除
2. When 記録対象の操作が行われた場合、the Activity Log Feature shall 操作者・操作日時・操作の種別を操作ログとして記録する
3. When 記録対象のフィールド変更が行われた場合、the Activity Log Feature shall 変更されたフィールドと変更前後の値を併せて記録する
4. When タスクの開発段階またはステータスが変更された場合、the Activity Log Feature shall 操作の起点となった画面（タスク詳細ページ・詳細モーダル・カンバンボード上での移動）にかかわらず、当該変更を記録する
5. The Activity Log Feature shall タスクの完了日時の変化を独立した操作ログとして記録せず、開発段階の変更の記録によって表す
6. When 開発段階の変更に伴い task-status-model の定めによってステータスが未着手へリセットされた場合、the Activity Log Feature shall 当該リセットを独立した操作ログとして記録せず、開発段階変更の記録に含める
7. When 繰り返しテンプレートによる自動生成など、ログインユーザーを起点としない記録対象の操作が行われた場合、the Activity Log Feature shall 操作者をシステムとして記録し、その由来を併せて記録する
8. The Activity Log Feature shall 操作ログをドメインイベントとして永続化し、アプリケーション運用ログ（アクセスログ・サーバーエラーログ等）とは独立に保持する
9. The Activity Log Feature shall 記録済みの操作ログの内容を事後に編集・削除する手段を提供しない

### Requirement 6: タイムライン表示
**Objective:** As a ワークスペースのメンバー, I want コメントと変更履歴を 1 つの時系列で確認できる, so that タスクに何が起きたかの経緯を一本の流れで追える

#### Acceptance Criteria
1. When ワークスペースのメンバーがタスク詳細ページを表示した場合、the Task Timeline shall 投稿されたコメントと表示対象の操作ログを 1 つの時系列として、発生日時順に表示する
2. The Task Timeline shall 記録対象のうち次のものだけを表示対象とする
   - 投稿されたコメント（本文・投稿者・投稿日時）
   - タスクのフィールド変更（タイトル／ステータス／優先度／詳細／担当者／案件関連付け／必須タスクフラグ／開発段階／親タスク／終了予定日）
3. The Task Timeline shall タスクの作成、タスクの削除、コメントの編集、コメントの削除を、タスクが論理削除済みであるかにかかわらず表示しない
4. When フィールド変更を表示する場合、the Task Timeline shall 次の文言で表示する

   | 操作 | 文言 |
   |---|---|
   | タイトル変更 | {操作者} がタイトルを {前} から {後} に変更しました |
   | ステータス変更 | {操作者} がステータスを {前} から {後} に変更しました |
   | 優先度変更 | {操作者} が優先度を {前} から {後} に変更しました |
   | 詳細変更 | {操作者} が詳細を更新しました |
   | 担当者変更 | {操作者} が担当者を {前} から {後} に変更しました |
   | 案件変更 | {操作者} が案件を {前} から {後} に変更しました |
   | 必須タスクフラグ変更 | {操作者} がこのタスクを必須タスクに設定しました／{操作者} が必須タスクの設定を解除しました |
   | 開発段階変更 | {操作者} が開発段階を {前} から {後} に移しました |
   | 親タスク変更 | {操作者} が親タスクを {前} から {後} に変更しました |
   | 終了予定日変更 | {操作者} が終了予定日を {前} から {後} に変更しました |

5. While フィールドの変更前または変更後の値が未設定である, the Task Timeline shall 当該の値を「未設定」として表示する
6. The Task Timeline shall 詳細の変更について変更前後の値を表示しない
7. When 投稿後に編集されたコメントを表示する場合、the Task Timeline shall 当該コメントが編集済みであることを示す
8. The Task Timeline shall 表示対象を「すべて」「コメント」「変更履歴」で絞り込む操作を提供する

### Requirement 7: 既存モーダルとの役割分担
**Objective:** As a ワークスペースのメンバー, I want カンバン／カレンダーのモーダルから詳細ページへ進める, so that 簡易確認から深い作業へスムーズに移行できる

#### Acceptance Criteria
1. The TaskDetailModal shall 簡易表示を基本とし、タイトル・優先度・開発段階・担当者・案件・詳細などの軽微な編集操作を提示する。ステータス変更の編集 UI は提示しない
2. The TaskDetailModal shall コメントの投稿およびタイムラインの表示を提示しない
3. When ワークスペースのメンバーがモーダル上でタスク詳細ページへの導線を選択した場合、the TaskDetailModal shall 当該タスクのタスク詳細ページへ遷移する
4. When 論理削除済みタスクをモーダルで開いた場合、the TaskDetailModal shall 参照専用とし、編集・削除操作を提示しない
