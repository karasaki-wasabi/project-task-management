## プロンプト本文（ここからコピー）

```text
プロジェクト名の提案: task-detail（タスク管理 — タスク詳細ページ）

目的
社内向けタスク/案件管理アプリ「Task Delivery Management」に、タスクの専用詳細ページを新設する。
現在はカンバン/カレンダーから開く TaskDetailModal だけがタスクの確認・編集手段で、
コメントや操作履歴を残す場所がない。詳細ページでタスクの CRUD・コメント・操作ログを
1画面にまとめ、モーダルは軽微編集専用に縮小する。見た目は既存アプリのデザインシステムを
厳密に踏襲する。Google Stitch は使わない。モックは実装前の確定用。

参照する既存の視覚言語（厳守。既存画面と地続きに見えること）
- ページ背景: bg-slate-50
- カード/サーフェス: bg-white
- 枠線: カード border-slate-200 / フォーム入力 border-slate-300 / 薄い区切り線 border-slate-100
- 角丸: カード・入力は rounded-md、モーダルパネルやドロップダウンは rounded-lg、バッジは rounded-full
- 影は控えめに使用: カード shadow-sm（hover で shadow-md）、モーダル shadow-xl、ドロップダウン shadow-lg/shadow-xl。重いドロップシャドウやグロー、グラスモーフィズムは禁止
- フォント: Noto Sans JP（見出し・本文とも同一ファミリー）。見出しは font-semibold、ラベルは text-xs font-medium text-slate-500
- アクセント: primary-600 (#1d4ed8) を主要操作ボタンに、hover は primary-700 (#1e40af)。フォーカスリングは focus:ring-2 ring-primary-500
- Primary ボタン: rounded-md bg-primary-600 px-3 py-1.5 text-sm font-medium text-white hover:bg-primary-700
- Secondary ボタン: rounded-md border border-slate-300 bg-white px-3 py-1.5 text-sm font-medium text-slate-700 hover:bg-slate-50
- Danger（削除系）: 非確定時は border border-red-300 bg-white text-red-700 hover:bg-red-50、確定操作は bg-red-600 text-white hover:bg-red-700
- 入力: rounded-md border border-slate-300 px-2.5 py-1.5 text-sm focus:border-primary-500 focus:ring-2 focus:ring-primary-500
- エラー表示: 画面上部の赤系アラートボックス（rounded-md bg-red-50 px-3 py-2 text-sm text-red-700）。フィールド横に赤文字を散らさない
- ヘッダー: sticky top-0、白背景、下線 border-slate-200、選択中タブは bg-blue-50 text-blue-700
- ダークモードなし、side-stripe（左色線）禁止、紫グラデーション禁止

既存 TaskDetailModal の現状（縮小対象・参考にする構造）
- 共通 Modal.vue に委譲、幅 max-w-xl
- 表示モード: ステータス・優先度・開発段階・担当者・案件をバッジ群で横並び表示、下にメモ欄（bg-slate-50 の枠付きテキストブロック）
- 編集モード: タイトル → 優先度/開発段階/担当者の横並びグリッド → 案件セクション（border border-slate-200 rounded-md p-3 で視覚分離、必須タスクのトグルスイッチ付き）→ メモ(textarea)
- コメント・タイムラインに相当するUIはアプリ全体に前例がないため、この機能はゼロから設計する

作ってほしい画面（デスクトップ幅を主、モバイルも破綻しないこと）

1) タスク詳細ページ（表示モード） `/workspaces/:workspaceId/tasks/:taskId` 相当
   表示項目: タイトル、ステータス、優先度、メモ、担当者、案件関連付け（案件・必須タスクフラグ）、
   開発段階、親タスク、子タスク一覧、予定日、完了日時
   - 上記フィールド群と、コメント＋変更履歴を統合した「タイムライン」を1画面にどう配置するか、
     レイアウト案を2つ出して比較してほしい（例: 左にフィールド・右にタイムラインの2カラム、
     または上部にフィールド・下にタイムラインの1カラム）
   - 完了種別または中止種別の開発段階にあるタスクでは、ステータスを表示しない状態も示すこと
   - 親タスク・子タスクは、それぞれのタイトルへのリンクとして表示する想定

2) タスク詳細ページ（編集モード）
   - タイトル・ステータス・優先度・メモ・担当者・案件関連付け・必須タスクフラグ・開発段階・親タスク・予定日を編集できる
   - 完了日時は編集不可（表示のみ、または非表示）であることが分かる見せ方にする
   - 親タスク選択で、既存の候補一覧からの選択 UI（検索可能なセレクトなど）を示す

3) タスク詳細ページ（論理削除済み・参照専用状態）
   - 編集操作を一切提示しない、閲覧のみの状態であることが一目で分かる表現（バナーやバッジなど）
   - タイムラインは表示したままでよい

4) コメント欄
   - コメント本文の投稿フォーム（複数行テキストエリア＋投稿ボタン）
   - 投稿済みコメントの一覧表示（投稿者名・投稿日時）
   - 自分が投稿したコメントにのみ編集・削除の操作が出る状態と、他人のコメントには操作が出ない状態の両方を示す
   - 編集済みのコメントに「編集済み」の表示がつく状態

5) タイムライン（コメントとフィールド変更の統合時系列）
   - 発生日時順の縦並びリスト。コメントとフィールド変更が混在する例を含めること
   - フィールド変更の文言例（そのまま使う想定の文言）:
     「{操作者} がステータスを {前} から {後} に変更しました」
     「{操作者} がメモを更新しました」（メモは変更前後の値を出さない）
     「{操作者} がこのタスクを必須タスクに設定しました」
   - 値が「未設定」から設定される変更の表示例も1つ含める
   - コメント・フィールド変更それぞれの視覚的な区別（アイコンや左のマーカーなど）があると望ましいが、
     side-stripe（左の太い色線）は禁止なので、それに頼らない区別方法にする

6) 既存 TaskDetailModal の縮小後の姿
   - ステータス変更・担当者変更・案件関連付けなど軽微な編集操作は維持する
   - コメント投稿・タイムライン表示は持たない
   - 「詳細ページを開く」ような導線（ボタンまたはリンク）を追加する。配置案を示してほしい

情報設計の制約（要件準拠）
- ステータスの値は「未着手・作業中・引継待ち・保留」（完了・中止は開発段階側で表現するため、ステータスの選択肢には含めない）
- ワークスペース横断の活動フィード、メンション通知、ストーリーポイント入力欄は出さない
- コメント・タイムラインのリアルタイム更新（WebSocketでの自動プッシュ）を前提にした見た目上の演出（「リアルタイム更新中」等）は不要

出力してほしいもの
- 上記 1〜6 の画面モック（1) は2案の比較を含む）
- 各画面の主要コントロール一覧（ラベル文言つき）
- 採用推奨案を1つ明示（特にタイムラインの配置と、モーダルからの導線の配置）
- デスクトップを主とし、狭い幅での崩れ方の注意があれば短く記す

トーン
Operate モードの実用ツール。装飾より走査性。タイムラインが情報過多に見えないよう、
視線の流れと余白の設計を優先する。
```
